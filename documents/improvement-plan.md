# UI/UX, Performance & Simplification Improvement Plan

## Context

This is a solo-maintained Next.js 16 / React 19 procedural fantasy map generator with a layered pipeline (Mesh → Topography → Hydrology → Population → Geopolitics). The codebase is generally disciplined (strict TypeScript, zero `any`/`@ts-ignore`, consistent `TProps` naming, no dead TODOs), but three full-codebase surveys (UI/UX, performance, simplification) turned up a consistent set of issues worth fixing as a coordinated initiative rather than piecemeal:

- **UI/UX**: a bespoke non-accessible modal, an abandoned design direction (unused Radix Tabs vs. a Select-as-tabs pattern), dead light-mode CSS with no toggle, hardcoded colors that break theme consistency, no loading/error boundaries, and only 8 total `aria-*` attributes in the entire app (all auto-generated by shadcn primitives, none authored).
- **Performance**: the generation pipeline is fully synchronous and blocks the main thread for up to 15,000 cells; `useThreeMap.ts` has a genuine O(n²) hotspot in vertex-elevation averaging plus up to 15,000 unmerged draw calls; `selectNationSeeds` in geopolitics scales with map size × nation count; whole-store Zustand subscriptions cause re-renders on every mouse move over the canvas.
- **Simplification**: `src/types/` (mandated by CLAUDE.md) doesn't exist — shared types live at `src/global.ts` instead; duplicated `clamp()`/`climateSuitability()` implementations; a 274-line context mixing React wiring with domain logic; a few files that exceed the 200-line convention without qualifying for a documented exception.

The goal of this plan is to work through all three areas in dependency order — cleanup first, then structural work, then risk-bearing performance/UX changes — so the app stays shippable after every phase.

**Decisions locked in before writing this plan:**
- Blocking pipeline → fix with a **Web Worker** (not main-thread chunking).
- Dead light-mode CSS → **remove it entirely** (dark-only going forward).
- `MapConfigDialog`'s Select-as-tabs pattern → **replace with the existing (currently unused) Radix `ui/tabs.tsx`**, removing the dead-code problem and the extra-click friction in the same move.
- Terrain-paint undo and multi-slot saved configs → **out of scope** (feature work, not cleanup/polish); current "Clear All Edits" + JSON export/import stays as-is.

## Phase 3 — Decompose `src/contexts/map.context.tsx`

Currently 274 lines mixing: context/state wiring, terrain-paint math (`paintTerrain`, lines 170-215), generation orchestration (`useEffect` + `setTimeout`, lines 116-152), and snapshot import/validation (`importFromSnapshot`, lines 88-114).

- Extract terrain-paint mutation logic → `src/services/terrain/paint.ts` (pure functions: `computeTargetElevation` is already in `terrainPainter.ts`; move the neighbor-blend + override-tracking logic here too).
- Extract snapshot import/validation → `src/services/pipeline/snapshot.ts`.
- Keep `map.context.tsx` as thin state wiring that calls into the above.
- Same-file quick fix while in here: `paintTerrain` (line 212) does `setMesh(prev => ({ ...prev, cells: [...prev.cells] }))` — a full shallow copy of up to 15k cells on **every paint stroke** during drag-painting. Replace with a targeted update (mutate the single changed + blended neighbor cells, bump a version/tick counter to drive memoization) instead of copying the whole array.

**Why do this before Phase 5:** this is a prerequisite for the Web Worker split — `MapGenerator.generate()` needs to be callable from a worker without being entangled in React state wiring, and this phase is what separates them.

## Phase 4 — Quick-win performance fixes

Independent of Phase 5; safe to ship on their own.

- `src/hooks/useMapCanvas.ts:23`, `src/hooks/useMapOverlay.ts:23` — replace whole-store `const {...} = useMapExplorerStore()` with fine-grained selectors (`useMapExplorerStore(s => s.displaySettings)` etc.), matching the pattern already used correctly in dialog components. `setHoverIndex` fires on every pointermove, so whole-store subscribers currently re-render on every mouse move over the canvas.
- `src/views/HomeView/MapCanvasPanel.tsx:120-128` — the `pointermove` handler calls `mesh.delaunay.find()` + `setHoverIndex` synchronously on every raw event. Gate it to one lookup per animation frame (rAF-coalesce).
- Consider moving `hoverIndex`/`hoverClientPoint` out of the persisted `mapExplorerStore` into local/ref state scoped to the canvas — they're transient UI-only values that don't belong in the same store as persisted generation config (bundle with the selector fix above, same code path).
- `src/services/rendering/canvas/index.ts` `renderLandCells` (lines 113-214) — collapses 6+ separate full passes over `landCells` (one per enabled display layer) into a single pass with per-cell layer branching. Verify visually against each display-mode toggle after the change.
- `src/services/geopolitics/nations.ts` `selectNationSeeds` (lines 293-370) — the clearest quadratic-ish hotspot: O(nationCount × landCells × seeds), rescanning all land cells per seed placement plus `estimateWaterCells` recomputation in inner loops (lines 338-344, 356-369). Pre-index land cells with a spatial grid/bucket instead of rescanning; hoist repeated `estimateWaterCells` results.
- `src/services/hydrology/river.ts` `fillDepressions` (lines 65-117) — replace iterative relaxation (up to `RIVER_CONFIG.depression.maxIterations = 200` full O(n) passes) with a priority-flood fill using the existing `TDeterministicMinHeap` (`src/services/utils/collections.ts`) — already proven for Dijkstra in `routeFinder.ts`. Turns O(n·200) worst case into O(n log n).
- Lower priority (small seed counts, lower ROI, same pattern): `src/services/geopolitics/capitals.ts:303-309`, `src/services/geopolitics/ethnic.ts:51`, `src/services/geopolitics/provinces/seed-split.ts:207,313`.

**Validation:** run `pnpm bench:map` before/after each hotspot fix — confirm measurable improvement and that seeded-RNG determinism is unchanged (same seed must still produce an identical map).

## Phase 5 — Web Worker pipeline + granular caching + three.js O(n²) fix

The riskiest phase — touches the core orchestrator and the 3D rendering path. Do this only after Phases 3-4 have de-risked the adjacent code.

**5a. Web Worker offload**
- Move `MapGenerator.generate()` (now cleanly separated from React after Phase 3) into a worker module (Next.js supports `new Worker(new URL(...))` module workers).
- `map.context.tsx` posts the config in, receives the generated mesh back via `postMessage`; replace the current `setTimeout(fn, 0)` one-tick defer (lines 121-152) with real worker message events.
- Confirm the mesh/cells payload is transfer-friendly (utils already lean on typed arrays per the perf survey — verify `TDelaunayMesh`'s `delaunay` object specifically, since `d3-delaunay` instances aren't structured-cloneable and will need to be rebuilt on the main thread from the raw points/cells the worker returns, similar to what `importFromSnapshot` already does at line 104).
- Wire a real progress UI (replaces the static "Generating map..." text — see Phase 6) once the worker can report per-stage progress.

**5b. Intermediate-stage caching**
- While restructuring the pipeline boundary anyway, extend `CacheManager.ts` to cache mesh+topography+hydrology separately from population+geopolitics, so changing `nationCount` alone doesn't force a full re-run through rivers/hydrology.

**5c. `useThreeMap.ts` O(n²) fix + draw-call reduction**
- `buildCellGeometry` (lines 35-72), called once per cell in the loop at lines 195-211: for every polygon vertex not yet in `vertexElevationCache`, it scans **all cells and all their polygon vertices** (`for (const c of cells) { for (const v of c.polygon) ... }`, lines 59-66) to find matches within 0.5 units. With 15,000 cells this is a genuine O(n²) hotspot, synchronous inside a `useEffect` keyed on `[containerRef, mesh]` (line 253) — reruns on every mesh regeneration while in 3D mode.
  - Fix: replace the linear scan with a spatial hash keyed by quantized vertex coordinates (e.g. round to the same precision as `vertexKey`, bucket cells by grid cell, only scan the local bucket) — same result, O(n) instead of O(n²).
- Each cell currently becomes its own `THREE.Mesh` (lines 206-210) — up to 15,000 draw calls. Merge the per-cell geometries into a single `BufferGeometry` via `THREE.BufferGeometryUtils.mergeGeometries` (cells already share one `sharedMaterial`, so a straight merge is enough — no need for `InstancedMesh` since there's no per-instance material variation, only per-vertex color which the merge preserves).
  - Keep `cell.id` addressability if anything depends on `mesh3D.userData.cellId` (check for consumers, e.g. click-to-select in 3D, before merging — if present, store an index range or id-per-vertex-group mapping on the merged geometry instead).

## Execution order & validation

Suggested sequence: **Phase 0 → 1 → 2 → 3 → 4 → 5 → 6 (can overlap with 4/5) → 7 → 8**.

Each phase is its own commit/PR sequence. Gate every phase — especially 0, 2, 4, and 5 — with:
- `runMapGeneration.test.ts` (existing test suite, covers generation correctness).
- `pnpm bench:map` (existing benchmark script) run before/after, to catch regressions and confirm the intended speedups.
- Manual smoke test in the browser: generate a map, toggle every display mode, open every config panel, open a nation/ethnic detail dialog, paint terrain and apply/clear, toggle 3D view, export/import JSON — since this app is canvas/interaction-driven and type checking alone won't catch rendering or UX regressions.
- For Phase 5 specifically: verify seeded-RNG determinism is preserved across the worker boundary (same seed + config must still produce a byte-identical mesh to the pre-worker implementation).
